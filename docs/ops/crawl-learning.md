## 当前可用行为

在明确启用 `CRAWL_LEARNING_ENABLED=1` 的应用中，来源Crawl config → 候选 → 含可用私有原始证据的preview，提供“Start bounded learning”。启动还会重新核对持久policy、来源代次、采样历史和证据文件。普通未保留原文的报告不足以学习；旧incomplete历史不能自动变成tracked。

启动意味着允许将**裁剪后的保留页面及当前recipe发送给显式分配的LLM供应商**。原始证据可能敏感，recipe/页面可能包含查询参数或其他私有数据；审核来源内容及供应商数据政策后再授权，不把敏感内部页面放入该流程。数据库仅保存暴露指纹和提示hash，不代表供应商不保留输入。

会话详情及来源近期列表可查看状态、最多3轮、反馈、费用和候选；同一capture重复启动仍是原会话，包括已取消的会话。取消仅在检查点阻止后续工作，不撤销已准入调用、不释放未知费用。

`awaiting_validation`只说明学习执行生成了候选，与下方当前验证结果分开。**现在有下述限定范围的独立留出报告，仍无validated/active或发布入口。** 保存候选不写Article、不派文章LLM，不替代现有日常爬虫。

## 失败冷却与人工安全重试（本地2c）

学习blocked/exhausted/cancelled后，同来源新委托至少冷却6小时，页面显示UTC时间。原capture仍只能访问原会话，不能通过新capture/重投清除冷却。成功候选的验证失败/证据过期不属于本切片自动触发的学习冷却。

blocked页面的“Request safe retry”仅适用于**整个会话从未有任何供应商预留**，并且原180秒期限、三轮限制、当前权限/证据/历史仍允许。填写原因；重复同一轮请求不覆盖审计，不重新开启终态。已有任何reserved/unknown/settled/reconciled等预留，即使最终费用为零也不能重试。取消/耗尽/过期不可恢复，不延长期限，不解锁未知费用。

这是原会话里的新一轮，不是新预算：操作者、时间、轮次和原因持久保留，原冷却不清除，原因不会发送给模型。表单可见也不是权限证明，提交时仍重查。SQL失败应查看原会话；提交成功但ACK丢失可能返回503，此时不要新建委托，重提同表单只确认原事件。派发失败保留queued，由启用的恢复器重派。

模型返回后、启动解析前再查权限/历史/所有权/剩余期限；过期恢复关闭calling状态而不重付费。不是完整租约接管/进程硬deadline。若原期限已过，只能等待冷却后按正常授权创建新证据委托，旧费用、暴露、验证选样和每日上限仍保留。

## 额度与异常

- 每会话US$0.20，Agent每日US$1，来源每日US$1，同时受全局LLM限制；UTC日按每笔预留的准入时刻。
- 最多20,000输入+输出计费token，含fallback。可信计费上界是供应商契约，不是tokenizer估计；缺审核拒绝。
- 金额/未知token占用不随取消、消息重投或日切释放。未知/在途学习预留还会保守阻止其他学习认领。
- 每会话启动后180秒检查点期限包含排队；并不是外部进程或数据库硬deadline。
- blocked时先查看状态原因及 `/admin/llm-usage`。执行/原文/SQL错误只显示固定信息，不记录敏感错误正文。
- 若账本reserved/unknown，按[预算对账规程](llm-budget-accounting.md)确认执行确已停止和最终供应商账单后处理；不能只因worker不见了就释放金额。
- 当前6小时冷却与有限人工重试见上文；新capture的新会话仍受共享来源/Agent预算，不得通过删表、改计数或重新标记queued恢复。

## 暴露历史检查（本地3a）

详情页的学习历史`tracked`仅说明受控学习会话/轮次连续、归属和输入指纹检查通过，不是独立留出通过，不覆盖其他模型任务、系统外输入或预训练。即使原始文件过期/清除，已记录的暴露仍保留；模型调用前丢ack也不把样本恢复成“未见过”。

当前协议为`crawl-learning.v3`，新增候选冻结和验证覆盖校验；旧v1/v2候选不补造冻结记录。3a暴露协议仍为visible-text.v1。迁移保留旧数据，但已有1b会话/轮次或crawl_schema费用历史时标记incomplete，不自动补hash或授予继续学习资格。缺标记/缺行/损坏记录会阻止新准入及候选落库，已经发生的费用仍结算。没有在线重新认证或清零入口；不要修改计数/complete或删除历史来恢复。数据库整体回退、旧调用方或拥有DB写权限者成套修改不由hash防护，必须另行审查。

`CRAWL_LEARNING_HISTORY_SCAN_LIMIT`默认4096，可配置为1–4096的整数，每类会话/暴露/重试审计最多检查该数量。不抽样放行、不自动裁剪；满时拒绝新记录。已有数量超过配置或配置非法时fail-closed。后续归档epoch/容量验证仍待设计，不能因到上限就删台账。规范化正文hash仅识别其既定清理/NFKC/大小写/空白规则内的复制，不是语义去重或完整污染检测。

## 派发与恢复

任务 `app.crawlers.learning_tasks.learn` / `recover` 明确路由到 `crawl_learn`。仅启用学习的beat安排30秒恢复扫描；默认关闭不产生恢复积压。每次最多选50份到期queued、过期active或缺派发状态的active；非到期running不占该选择。运行中到期或缺状态时转blocked，**不会自动再次发起可能已经付费的尝试**。

`learning-delivery.v1`消息携带会话ID与派发键，绑定原输入hash、当前已消耗轮次及人工retry计数。重投旧payload不能认领有效的新阶段，未认领的旧错误也不能关闭它；已知损坏history则先隔离blocked。键不是权限证明，实际认领/每次付费仍检查policy/evidence/history/当前配置及预算。

同阶段的派发槽位先持久提交，再调用broker；按记录UTC准入时刻至少保留30秒（存储为floor(now)+31s），重复POST/并发恢复共享这个间隔，broker失败或提交ACK丢失也不立即重发。**这不是网络发送速率保证**：慢COMMIT/RPC可越过时窗后晚到重复，仍依赖消费fence。页面的协议、消息指纹与下次资格时间都不是broker收到确认或新期限；等待消耗原180秒，没有为排队延长的入口。

当前worker仍可在同一次任务中执行最多三轮，但只有自己的训练拒绝事务提交确认后才取得下一轮continuation键。若确认丢失，旧消息不猜测继续；恢复器读取已提交的下一轮queued重新派发。已结算旧轮次之后继续原有授权轮次，不等同于重复旧attempt或人工安全retry。缺派发状态的旧active不自动补权，旧单参数消息被新worker忽略；终态/候选/验证历史继续可读。

认领在证据/暴露准备后、付费在最后权威/配额查询后核原deadline，避免慢读取越过检查；关闭/recover自身存储失败只记固定日志。依然没有SQL写/COMMIT/SDK硬deadline、完整lease或exactly-once保证。

现在提供本地可选`docker-compose.learning.yml`及`crawl-learning` profile；统一启用标记仍默认0，启动guard拒绝未启用/缺RO私有目录/旧schema。运行和健康门禁见[学习worker说明](learning-worker.md)，不能把配置或snapshot通过当作真实消费者/容量通过。

消息丢失后的恢复依赖beat和该队列消费者都可用。关闭beat/worker、长队列拥塞或DB不可用时，不承诺及时终态；Admin仍可取消会话。状态、attempt和已提交预留保留，不将未知外部结果伪称成功或免费。
