## What changes in production

- **Scheduling**: beat drops `daily-crawl-all` and `crawl-frequency-check` and runs `dispatch_due_crawls` every 60 s.
  One next-due rule per source (frequency plus the 01:00 Europe/Paris anchor), at most 4 claims per minute, a
  15-minute lease with a fence, retry backoff, 24 h cooldown plus an attention flag for access failures.
- **Crawl writes**: every run (legacy crawler or approved recipe) writes articles, their LLM jobs, the run log and
  the next due time in one fenced transaction. No recipe is approved yet, so every source keeps its legacy crawler.
- **LLM**: new articles get a durable `article_llm_job`; `app.llm.article_tasks.process` claims it before any paid
  call; `recover` runs every 60 s. The post-crawl rescan of unprocessed articles is gone; old
  `process_article_llm` and single-argument `crawl_source` messages are converted, never run directly.
- **Admin**: approve/reject/rollback/retire recipes, source route/next-due/attention, crawl-log route/outcome/code,
  "crawl now" only requests; the check-interval setting is removed.
- **Migration** `b9d4f6a2c813` (expand-only): three new tables, four profile columns, eight crawl-log columns.
  Old code ignores all of them, which is what makes image rollback safe.

Delta versus `7ec578c`: `app/`, `celery_app.py`, one migration, `scripts/`, tests, docs. No `requirements/`,
`docker/` or Compose change; the script refuses to continue otherwise.

## Script steps (`~/.cache/fsi-release/m2_release.sh`, run on the VPS with the expected head as argument)

1. Release lock. Clean checkout containing `7ec578c`; the four apps on the m34c images; `origin/master` equals
   the expected head and contains the checkout; no infra paths in the delta. Fast-forward.
2. Build the four images while the old containers run; tag `candidate-<tag>`. `pip freeze` and Python version
   identical to each running container; images contain `app/crawlers/runs.py` and `app/llm/article_tasks.py`.
   New pin layer copied from the m34c layer with only images replaced. Candidate head must be `b9d4f6a2c813`.
3. Ledger snapshot (reservations by state, today's usage).
4. Stop beat; wait until both workers reply with no active/reserved tasks (≤ 10 min); record queue lengths; stop
   workers (180 s grace) and web.
5. `mysqldump` backup (0700 dir, 0600 file), gzip test, trailer, SHA-256.
6. `flask db upgrade`; require `b9d4f6a2c813 (head)`, the three new tables empty and the new columns present.
   Run `scripts/backfill_article_jobs.py` (dry run, then `--apply`) and record both counts.
7. Start web and both workers from the new pin; wait for health; require the llm worker to register
   `app.llm.article_tasks.process` and the fast worker `app.crawlers.tasks.dispatch_due_crawls`. Ledger again
   and require it unchanged (no beat yet, so no work). Start beat last.
8. Acceptance: wait for the first `dispatch_due_crawls` and `article_tasks.recover` successes, require one
   `crawl_source_state` row per active source, show images, restarts, public health and recent error lines.

If anything fails after step 4, the script restarts all four apps from the m34c pin (the additive schema stays;
never an automatic database restore).

## Rollback after acceptance

Stop beat, drain the queues as in step 4, then
`docker compose -f docker-compose.yml -f docker-compose.prod.yml -f docker-compose.caddy.yml -f docker-compose.evidence.yml -f ~/fsourceinsight-backups/m34c-20260924171323/candidate.compose.json up -d --no-build web worker worker_fast beat`.
New tables and columns stay and are ignored; queued `article_llm_job` rows become inert; the old frequency check
and unprocessed-article rescan resume. Do not run old and new workers together.

## CI run 1 on `b32153d` and correction (recorded before the release)

Run 36115346994: offline job 1229 passed / 26 skipped; `mysql-integration` 4 failures + 1 error, so the worker
lifecycle gate after it did not run. All five were test defects, not production code:

- Three MySQL LLM tests still called the retired direct task `process_article_llm`, which now only creates a job.
  They test pipeline-level behaviour, so they call `app.llm.pipeline.process_article` directly (as the offline
  pipeline tests already do).
- Two crawl tests read through a REPEATABLE READ snapshot that their session opened before the runs committed in
  their own sessions; they now start a fresh transaction before asserting.
- The worker lifecycle gate used Admin "Crawl now" to publish tasks, which since M2 only marks a source due. It now
  uses the startup-discovery scan (a real Admin action publishing one crawl-queue task) for the 100-task count
  case, and a claimed `crawl_source` for the memory case. `crawl_source` stores its result again, as it did
  before M2 (the plan had added `ignore_result`).

Correction commit `f0312b2`; the release waits for its CI.
